## Reading the user's Telegram and WhatsApp through BotChatter

BotChatter is a hosted MCP server, `botchatter`, at `https://staging.botchatter.ai/mcp` (streamable HTTP, OAuth 2.1 with PKCE, dynamic client registration; no token in any file). Add it with `codex mcp add botchatter --url <url>` or `claude mcp add --transport http botchatter <url>`, then sign in (`codex mcp login botchatter`, or `/mcp`): enter an email, type the emailed 6-digit code, approve (the first time, save the recovery code the page shows once). If Telegram is not connected yet, the consent button is "Allow and connect Telegram": scan the QR code with Telegram (Settings → Devices → Link Desktop Device, or tap the `tg://` link on the phone), and the browser returns to the assistant. WhatsApp (beta): `connect_account({provider:"whatsapp"})`; the link opens `/connect/whatsapp`, shown on a computer or second screen (not the same phone), and the user scans it from WhatsApp → Settings → Linked devices → Link a device.

Tools (17, all bounded, 30 calls a minute per account): `connection_status()` first; `connect_account({provider:"telegram"|"whatsapp"})` returns a 30-minute `connect_url` (`/link/cl2.…`, carrying a 2-hour device unlock: a secret, for the account's own human only, never posted publicly or written to files). Reading: `catch_up({provider?, since?, max_chats<=20, per_chat<=10})` is the one call for "what's new"; `get_mentions` for what needs an answer; `find_chats({query, type?})` to locate a chat by name; `list_recent_chats({limit<=20, provider?})`; `get_chat_info({chat_ref})`; `find_contacts({query})` (phones masked); `read_recent_messages({chat_ref, limit<=30, before?})` returns `{provider, messages, sync?}` and never marks read; `get_message_context({chat_ref, message_id})`; `search_messages({query, provider?, chat_ref?, type?})`; `get_media({chat_ref, message_id})` (up to 5 MB). Results merge both providers unless `provider` is given; `chat_ref` starts with `cr1.` (Telegram) or `wr1.` (WhatsApp): pass it back unchanged. On WhatsApp `sync.state:"partial"` means older messages may be missing (it only has what arrived while connected): say so, never claim there are none. Replies: `request_reply_approval({chat_ref, text})` shows the user an approval form in the chat (the app renders it; you cannot answer it); they can edit the text, then approve or decline. Approved, it is sent once, exactly as approved, and the result has state `sent`; declined is `rejected`; unanswered after about 2 minutes is `pending` (a late answer still applies; it expires unsent after 15 minutes). Sending needs the Plus plan, and apps that can't show approval forms cannot send or change privacy rules. Never say it was sent unless the result or `list_reply_requests` shows state `sent`; `failed` with `ambiguous:true` may or may not have been delivered: tell the user to check the chat and never re-request automatically; `cancel_reply_request` withdraws a stale pending one. WhatsApp replies only go to chats where the other person wrote first. Privacy: the user can hide chats (blocklist or allowlist); "hidden by the user's privacy settings" means do not work around it; you can only propose rules with `propose_privacy_rules`, which the user accepts or declines in a form in the chat (`get_privacy_settings` shows the mode). Prompts: `catch_me_up`, `draft_replies`, `classify_chats_for_privacy`.

Autonomous agent with its own mailbox (no browser): `GET <web>/api/agent/` describes; `POST <web>/api/agent/signup {email, agent_name}` emails a code; register a public client at `/oauth/register` (redirect `http://127.0.0.1:8976/callback`, auth method `none`); build a PKCE S256 `/authorize` URL with `scope=telegram` and `resource=<web>/mcp`; `POST <web>/api/agent/authorize {email, code, authorize_url, recovery_code?}` returns `redirect_to` with `code` (check `state`); the first time it also returns `recovery_code` once: store it in a secret store, never print it, and send it on every later authorize for that account, else 403 `recovery_code_required` (the emailed code is then used up); exchange at `/oauth/token` with the verifier; call `/mcp`; then `connect_account` and give the link to your human. Keep tokens and the recovery code in a secret store; never print them or the emailed code. The plugin's `scripts/agent-signup.sh` (POSIX sh, curl, openssl) does all of it. An address that belongs to a browser-created account answers 409: that person signs in normally.

Etiquette: read only when the user asked in this conversation; say which chat you open; prefer `catch_up` over listing chats and reading each one, and `find_chats` to locate a chat by name; at most 20 chats and 30 messages per call, start smaller; ask before opening media or contacts unrelated to the request; phone numbers are masked by default, do not try to unmask them; summarize instead of dumping messages, quote only when asked; do not copy message contents into files or other tools. Show drafts first, request approval only for the ones the user confirms, tell them an approval form will appear in the chat, and never pressure the human to approve or approve on their behalf. "Telegram is not connected. Ask the user to open <url> …": show that link, wait for them, then `connection_status` and retry once. "Rate limit: at most 30 BotChatter calls per minute", "Telegram is rate-limiting this account. Try again in N …" or a sign-in 429: stop, tell the user, retry once after the stated time; never loop. HTTP 401, or "Encryption keys changed; connect this assistant again" on refresh: sign in again. Privacy (Telegram and WhatsApp): "encrypted with a key that only you, and the AI apps you connect, can unlock. We don't keep that key."; WhatsApp: "We connect to WhatsApp only while you're using your assistant. Messages that arrive while you're away are fetched next time, within WhatsApp's limits." WhatsApp is beta. Never say "end-to-end encrypted" or "zero-knowledge".
